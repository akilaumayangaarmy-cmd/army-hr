# Army HR Data Migration Frontend

A lightweight React application built with Vite, Tailwind CSS, and Lucide‑React icons.

## Features
- Drag‑and‑drop (or click) Excel/CSV upload using **react-dropzone**.
- In‑browser parsing with **SheetJS (xlsx)**.
- Master-data ID checks for `OLD_ID` values in the temporary members table against the District and Provinces tables.
- Validation against static master‑data lists (replace with API calls in production).
- Summary cards showing total, valid and missing records.
- Table of rows with missing master data and quick **Add** buttons to create new master entries on the fly.
- Responsive design with a subtle army‑green theme.

## Backend API
The backend reads uploaded Excel and CSV files in memory and upserts their rows
into the configured Oracle table using `OLD_ID` as the unique key. Matching
members are updated, new `OLD_ID` values are inserted, and existing members not
present in the upload are never deleted. After each upsert, matching rows in
`PNRDB_DEV."temp_members"` have their province, district, and divisional
secretariat UUIDs refreshed from the corresponding master tables. These updates
are committed or rolled back together with the master-data upsert. Uploads are
limited to 100 MB.

In a second terminal, start the API:
```bash
cd "C:/Users/user/Desktop/New folder/data_migration/backend"
npm install
npm run dev
```
The frontend proxies `/api` requests to `http://localhost:3001`.
`POST /api/upload` accepts a multipart form field named `file`. The first
worksheet must contain an `OLD_ID` column with a unique, non-empty value for
each row. Other headers must match destination-table column names. The endpoint
returns the parsed rows and a `processed` count after the database transaction
succeeds.

The migration page also provides a **Sync temp member location IDs** button.
It calls `POST /api/temp-members/sync-location-ids` to refresh location IDs for
all matching `temp_members` rows from the current master data and reports how
many records were updated.

`GET /api/master-data/check/district` and
`GET /api/master-data/check/provinces` compare distinct, non-empty
`DISTRICT_ID` or `PROVINCE_ID` values in
`PNRDB_DEV."01_Temp_members_master_data"` with `"old_id"` in the quoted
`PNRDB_DEV."districts"` or `PNRDB_DEV."provinces"` table. Each response
contains per-ID `MATCHED`/`UNMATCHED` statuses and summary counts.

## Customisation
- Replace the static `masterData` object in `src/App.jsx` with calls to your backend to fetch real master data.
- Extend the validation logic to cover all columns from your Oracle `members` table.
- Implement the **Export / Proceed** button to POST the cleaned data to your migration API.
